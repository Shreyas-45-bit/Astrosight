2. Architecture Mapped to Tech

Birth details → geopy + timezonefinder → zoneinfo (local→UTC) → swe.julday
  → pyswisseph (positions, Ascendant, houses)
  → vedic_features.py (pure Python + pydantic models)
  → Chart JSON
      → retriever.py (Supabase metadata filter + pgvector similarity)
      → context_builder.py → LLM API → response

Palm image → OpenCV preprocessing → MediaPipe/segmentation → line detection
  → feature extraction → PyTorch model → palmistry knowledge / LLM

Each box stays in its own module, so the astrology and palm pipelines never share code paths.

4. Astronomical and Vedic Computation

Component Tech Notes
Planet positions, Ascendant, houses pyswisseph (import swisseph as swe) 🔒 Never use an LLM or approximate formulas.
Julian Day swe.julday / swe.utc_to_jd 🔒 Use Swiss Ephemeris functions, not a custom formula.
Sidereal mode swe.set_sid_mode(swe.SIDM_LAHIRI) 🔒 Set once from a central AYANAMSHA config.
Node handling Rahu = mean or true node from Swiss Ephemeris, Ketu = Rahu + 180° Document which node type you use.
Ephemeris data files Set with swe.set_ephe_path() Swiss Ephemeris data files give full precision; without them it falls back to the built-in Moshier calculation, which is less precise. Record which mode is active.
Local time → UTC zoneinfo (stdlib) Handles historical DST.
Place → lat/long geopy (Nominatim) or a geocoding API 💡 Cache results; user can also enter coordinates manually.
Lat/long → timezone timezonefinder 💡
Feature engine Pure Python + pydantic models Rashi, nakshatra, pada, dignity, aspects, vargas, Vimshottari dasha, yogas.

Licensing note: Swiss Ephemeris is dual-licensed (open-source AGPL or a paid professional license). Fine for an academic project, but check terms if you ever commercialize.

5. BPHS Knowledge Base Pipeline

Stage Tech Notes
Text extraction PyMuPDF (fitz) 💡 Fast, gives page-level text and lets you keep PDF page numbers.
Layout-sensitive pages pdfplumber 💡 Only if PyMuPDF output is jumbled.
Scanned or unclear pages OCR (e.g. pytesseract) 💡 Add only if pages have no text layer. Flag output needs_review; never guess.
Chapter detection Regex over headings and the table of contents Map printed page ≠ PDF page separately.
Atomic rule splitting Rule-based Python parsing first; optionally LLM-assisted with human review The LLM may segment and tag text but must copy source_text verbatim. Verify with a diff check.
Storage format JSONL (one object per line) 🔒
Validation validate_jsonl.py + pydantic schema 🔒 Checks IDs, pages, duplicates, house range.
Data handling / reports pandas 🔒 (evaluate) Counts per chapter, house, planet, topic.

Do not add PDF libraries you don't end up using.

6. Embeddings

The provider and model are configurable (EMBEDDING_PROVIDER, EMBEDDING_MODEL), and vector dimension must follow the model.

Option Type Typical dimension Pros / cons
Hosted API embedding model (e.g. OpenAI text-embedding-3-small) API 1536 (model-dependent) Simple, strong quality, needs a key and internet.
sentence-transformers (e.g. BAAI/bge-small-en-v1.5, all-MiniLM-L6-v2) Local 384 (model-dependent) Free, offline, good enough for a student project.
  • Read the dimension from the model at runtime (or a config map) and pass it to the SQL migration. Never hard-code 1536.
  • Embed the retrieval_text field (structured label + source text), not metadata alone.
  • Use numpy for batching and normalization.
  • If you change the model, re-embed everything; vectors from different models are not comparable.

7. Database and Retrieval

Component Tech Notes
Database Supabase PostgreSQL 🔒 Single managed service.
Vector search pgvector 🔒 Table bphs_rules with an embedding column.
Client supabase Python client (or psycopg for bulk loads) 🔒 Use the service-role key only in backend and scripts.
Vector index HNSW (or IVFFlat) with the operator class matching your distance metric (cosine recommended) Migration 001_create_bphs_rules.sql.
Metadata indexes B-tree on house, planet, chapter, rule_type, topic 🔒
Retrieval SQL function/RPC: metadata WHERE filter, then ORDER BY embedding <=> query_embedding 🔒 Filter first, similarity second.

Optional (only if needed): add full-text search (tsvector) as a hybrid signal. Skip for v1.

10. Palm-Reading Module

Kept fully separate from the astrology code (src/palm/ recommended).

Stage Tech
Image validation (format, size, blur, hand present) Pillow, OpenCV, MediaPipe Hands
Preprocessing (resize, normalize, contrast, denoise) OpenCV (e.g. CLAHE, Gaussian blur)
Palm segmentation / ROI MediaPipe hand landmarks or a small U-Net (PyTorch)
Palm-line detection Classical CV (Canny / ridge filters such as Frangi via scikit-image) or a U-Net trained on line masks
Feature extraction Line length, curvature, position, intersections (NumPy / scikit-image)
ML / CV model PyTorch (or scikit-learn for simple classifiers on extracted features)
Interpretation Palmistry knowledge base + LLM, same provider interface as section 8

Open dependency: you'll need a palm-image dataset and a palmistry knowledge source. Neither is defined yet, so decide these early.

14. Hard Constraints (from your prompt)

  • Swiss Ephemeris, not the LLM, does all astronomical calculation.
  • Sidereal zodiac with Lahiri by default and configurable.
  • BPHS Vol I and II PDFs are the only classical source; no other editions or websites.
  • Supabase + pgvector only (no second vector database).
  • Retrieval = metadata filter + vector similarity.
  • No Kubernetes, microservices, GNNs, fine-tuning or unnecessary agents in v1.
  • Palm pipeline stays separate from the astrology pipeline.
