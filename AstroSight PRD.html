AstroSight: Product Requirements Document

Version: 1.0 (draft) | Type: Final-year project | Date: 29 Sep 2026

Source: derived from the project prompt (astro_whole_prompt.txt / asrto_prompt.pdf). Items not stated in the prompt are marked [Assumption] and listed in section 14.

1. Overview

AstroSight is an AI-based computational Vedic astrology and interpretation system. It integrates astronomical computation, classical astrological rules, retrieval-augmented generation (RAG) and natural-language AI.

It has two independent pipelines:

  1. Astrology pipeline: birth details → Swiss Ephemeris → Vedic feature engine → structured chart → RAG over the Brihat Parashara Hora Shastra (BPHS) → LLM interpretation.
  2. Palm-reading module: palm image → computer vision / ML → palm features → palmistry knowledge / LLM → interpretation.

Academic framing: AstroSight implements computational Vedic astrology and AI-assisted interpretation. It makes no claim that astrology is scientifically proven.

2. Problem Statement

  • LLMs cannot calculate planetary positions reliably, and they hallucinate astrological "rules".
  • Generic astrology apps rarely cite classical sources.
  • Classical texts such as BPHS are long, unstructured and hard to query for a specific chart.

AstroSight separates calculation (deterministic), knowledge (source-verified BPHS rules) and interpretation (LLM, grounded and traceable).

3. Goals and Non-Goals

Goals

  • G1. Compute accurate sidereal planetary positions and the Ascendant with Swiss Ephemeris.
  • G2. Convert those positions into structured Vedic features (rashi, nakshatra, dashas, yogas, etc.).
  • G3. Build a source-faithful BPHS knowledge base of atomic rules from the supplied Volume I and II PDFs.
  • G4. Retrieve only the rules relevant to a given chart, using metadata filtering plus vector similarity.
  • G5. Produce personalized interpretations that separate calculated facts, classical rules and synthesis, with every rule traceable to chapter and page.
  • G6. Provide a separate palm-reading module.

Non-Goals (v1)

  • No LLM-computed planetary positions, and no third-party astrology API as the primary calculation engine.
  • No fine-tuning, Kubernetes, microservices, graph neural networks, unnecessary agents, multiple vector DBs or extra cloud services.
  • No merging of other editions, translations, websites or astrology systems into the BPHS knowledge base.
  • No public redistribution of the translated BPHS text.
  • No mixing of the palm image pipeline with the astronomical pipeline.

4. Users and Use Cases

Persona Need
End user / seeker Enter birth date, time and place; get a readable, personalized chart interpretation. Optionally upload a palm image.
Academic evaluator Verify that every interpretation traces to a BPHS rule (volume, chapter, printed page, PDF page, rule ID).
Developer / project owner Run the extraction, validation, embedding and upload pipeline; review flagged records; test retrieval.

Key user stories

  • As a user, I enter my birth details and receive my sidereal chart (Lagna, planets, houses, nakshatras, dashas, yogas).
  • As a user, I ask about career, marriage, wealth or education and get an answer grounded in relevant BPHS rules.
  • As an evaluator, I can see which source passage backs each statement.
  • As a developer, I can see which extracted rules and pages need manual review.
  • As a user, I upload a palm photo and receive palm-feature-based insights. [Assumption: presented separately from the chart reading]

5. System Architecture

USER (date, time, place)
  → Location + Timezone → Local time → UTC → Julian Day
  → SWISS EPHEMERIS (positions, Ascendant, houses)
  → VEDIC FEATURE ENGINE
  → STRUCTURED BIRTH CHART (JSON)
        ├→ Rule Engine
        └→ RAG Retrieval (Supabase + pgvector)
              → Relevant BPHS rules → Context Builder → LLM → Personalized response

PALM IMAGE → Validation → Preprocessing → Segmentation → Line detection
  → Feature extraction → ML/CV → Palm features → Palmistry knowledge / LLM → Interpretation

Responsibility separation (must not be merged):

Layer Responsibility
Swiss Ephemeris Astronomical calculation
Vedic Feature Engine Structured Vedic calculations (no natural language)
BPHS Knowledge Base Classical rule source
Supabase pgvector Storage and retrieval
RAG Relevant knowledge retrieval
LLM Natural-language interpretation
Palm ML/CV Image-based palm analysis

6. Functional Requirements

6.1 Astronomical Engine (src/astrology/ephemeris.py)

ID Requirement Priority
FR-1.1 Use pyswisseph (import swisseph as swe); independent of the LLM and RAG. Must
FR-1.2 Calculate Sun, Moon, Mars, Mercury, Jupiter, Venus, Saturn, Rahu and Ketu. Must
FR-1.3 Preserve per body: longitude, latitude (where available), speed, retrograde status, sign, degree within sign, and raw values before Vedic conversion. Must
FR-1.4 Use the sidereal zodiac with Lahiri ayanamsha (swe.SIDM_LAHIRI) by default; ayanamsha is configurable via one central config value (no hard-coding across files). Must
FR-1.5 Treat birth time as local civil time; convert place → lat/long → timezone → UTC → Julian Day using Swiss Ephemeris functions (no custom approximations). Must
FR-1.6 Preserve original date, time and place, plus lat, long, timezone, UTC datetime and Julian Day. Must
FR-1.7 Calculate Ascendant (longitude, sign, degree) and house cusps under a single, documented, configurable house system. Must
FR-1.8 Output must be deterministic for identical input. Must

6.2 Vedic Feature Engine (src/astrology/vedic_features.py)

ID Requirement Priority
FR-2.1 Compute rashi, nakshatra, nakshatra pada, lagna and bhava/house placement. Must
FR-2.2 Compute dignity (exaltation, debilitation, own sign), planetary relationships, retrograde status and aspects. Must
FR-2.3 Compute Vimshottari Dasha and Antardasha. Must
FR-2.4 Detect relevant yogas and compute relevant vargas (divisional charts). Should
FR-2.5 Produce structured output only, with no natural-language interpretation. Must

6.3 Standard Chart JSON (src/astrology/chart.py)

ID Requirement
FR-3.1 One JSON format is the bridge between the astronomical engine, feature engine, RAG and LLM.
FR-3.2 Sections: birth_data, settings (zodiac, ayanamsha, house_system), ascendant, planets, houses, nakshatras, dashas, yogas.

6.4 BPHS Knowledge Base

ID Requirement Priority
FR-4.1 Use only the supplied BPHS Vol I and II PDFs (Girish Chand Sharma translation) as the source of truth. Must
FR-4.2 Inspect both PDFs and create data/source_inventory.json with only verifiable metadata. Must
FR-4.3 Create data/chapter_map.json for every chapter, keeping printed page and PDF page as separate fields. Must
FR-4.4 Extract atomic rules (not chapter-sized chunks). Examples: planet in house, house lord in house, aspects, dignities, relationships, vargas, strengths, karakas, yogas, dashas, ashtakavarga, avasthas, argala, upapada, bhava pada, remedies. Must
FR-4.5 Every rule keeps source_text, plus context_text where needed, without unnecessary paraphrasing. Must
FR-4.6 Rule metadata: rule_id, source_id, book_title, volume, translator, chapter, chapter_title, printed_page, pdf_page, house, planet, sign, nakshatra, rule_type, topic, priority, extraction_status. Use null where not applicable. Must
FR-4.7 Use a controlled rule_type vocabulary (e.g. planet_in_house, yoga, dasha, ashtakavarga; fallback other). Must
FR-4.8 Uncertain OCR or extraction is flagged needs_review and unreadable pages go into a review report. Never guess. Must
FR-4.9 Organize output into data/bphs/houses/house_01…12.jsonl plus planets, signs, vargas, aspects, strengths, yogas, karakas, dashas, ashtakavarga, avasthas, special_rules. Use tags for multi-topic rules; avoid duplicates. Must
FR-4.10 JSONL: one object per line, not wrapped in an array. Must
FR-4.11 Priorities: Vol I = planets, signs, vargas, aspects, houses 1–12, lords, Rahu/Ketu, strengths, karakas, yogas, avasthas. Vol II = Vimshottari and other dashas, ashtakavarga (Shodhana methods), Sudarshana Chakra, Panchamahapurusha yogas, gunas. Classify high/medium/low; delete nothing. Must

6.5 Ingestion, Embeddings and Storage

ID Requirement
FR-5.1 Scripts: extract_bphs.py, validate_jsonl.py, generate_embeddings.py, upload_to_supabase.py, test_retrieval.py.
FR-5.2 validate_jsonl.py checks JSON syntax, required fields, IDs, chapter, both page fields, source_text, extraction_status, valid house number and duplicate rule IDs. It writes reports/validation_report.json.
FR-5.3 retrieval_text combines structured info and source content (e.g. "First House. Sun in First House. Personality. [source text]"). Never embed metadata alone or mix unrelated chapters.
FR-5.4 Embedding provider and model are configurable via .env; vector dimension follows the selected model (not hard-coded to 1536).
FR-5.5 Supabase PostgreSQL + pgvector; migration 001_create_bphs_rules.sql; table bphs_rules with the fields in FR-4.6 plus id, source_text, context_text, retrieval_text, metadata, embedding.
FR-5.6 Indexes on house, planet, chapter, rule_type, topic and vector similarity (pgvector-compatible).
FR-5.7 .env.example with EMBEDDING_PROVIDER, EMBEDDING_MODEL, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY. No real keys committed.

6.6 RAG and Interpretation

ID Requirement
FR-6.1 src/rag/retriever.py: filter by structured metadata first (e.g. {house: 10, planet: Mars, topic: career}), then rank by vector similarity. Do not rely on semantic similarity alone when chart facts are known.
FR-6.2 Chart-aware retrieval: from the chart JSON, identify relevant conditions (planet in house, house general rules, house lord, aspects, dignity, yogas, strength). Never send the whole book to the LLM.
FR-6.3 src/rag/context_builder.py: pair each CHART FACT with its RELEVANT BPHS RULE and SOURCE (volume, chapter, printed page, rule ID).
FR-6.4 prompts/astrology_interpretation.txt: the LLM receives the chart, Vedic features, retrieved rules and source metadata. It must not compute positions or invent rules, and must clearly separate (A) calculated facts, (B) classical rule statements and (C) synthesized interpretation.
FR-6.5 Traceability: every rule-based statement carries source, volume, chapter, chapter title, printed page, PDF page and rule ID.

6.7 Palm-Reading Module (separate)

ID Requirement
FR-7.1 Pipeline: image validation → preprocessing → palm segmentation → palm-line detection → feature extraction → ML/CV → palm features → palmistry knowledge/LLM → interpretation.
FR-7.2 Fully isolated from the astronomical astrology pipeline.
FR-7.3 [Assumption] Palmistry knowledge source, model choice and datasets are not yet defined; see Open Questions.

7. Non-Functional Requirements

Category Requirement
Accuracy Positions come only from Swiss Ephemeris; no hard-coded fake test values. Expected values are generated from the actual calculation.
Fidelity No invented rules; source text preserved; uncertain extractions flagged.
Determinism Identical input gives identical chart output.
Traceability Chart facts, retrieved rules and interpretation statements link back to source.
Configurability Ayanamsha, house system, embedding provider and model are configurable centrally.
Simplicity Simplest reliable architecture; minimal dependencies (pyswisseph, pydantic, python-dotenv, supabase, numpy, pandas, and PDF libraries only if needed).
Security Secrets only in .env; service-role key never committed.
Legal Provenance preserved; no public redistribution of the full BPHS translation; no scraping of external sites to replace the PDFs.
Maintainability Clear module separation; README covers setup, pipeline, limitations and the manual review process.

8. Data Model Summary

  • Chart JSON: birth data, settings, ascendant, planets, houses, nakshatras, dashas, yogas.
  • Rule record (JSONL / bphs_rules): see FR-4.6, with example ID pattern BPHS_V1_CH14_P194_H1_SUN_001.
  • Reports: validation_report.json (total, verified, needs_review, duplicates, missing source text) and knowledge_base_report.json / .md (chapters, rules per chapter/house/planet/topic, review items, problem pages, duplicates, missing metadata).

10. Delivery Plan (Extraction Workflow)

Do not process all pages blindly on the first run.

Phase Steps
1. Inspect Inspect both PDFs; create source_inventory.json and chapter_map.json.
2. Sample Extract 1–2 Vol I chapters and 1 Vol II Dasha section. Validate chapter detection, both page numbers, source text, rule splitting, metadata and JSONL validity.
3. Scale If the sample is correct, process remaining chapters; generate the full JSONL knowledge base; run validation.
4. Embed and store Generate embeddings; create the Supabase migration; upload records.
5. Test Run retrieval tests and Swiss Ephemeris tests.
6. Report Generate final reports and README.

11. Testing and Acceptance Criteria

Ephemeris tests (tests/test_ephemeris.py):

  1. A valid birth date/time converts to Julian Day.
  2. Swiss Ephemeris returns planetary positions.
  3. Sidereal mode is active and Lahiri ayanamsha is configured.
  4. The Ascendant calculation returns a valid result.
  5. Longitudes fall within valid ranges (0–360°).
  6. Retrograde information can be represented.
  7. Output is deterministic for identical input.

Retrieval test cases (tests/test_retrieval_cases.json): Sun in 1st, Venus in 7th, Mars in 10th, Jupiter in 5th, career query, marriage query, wealth query, education query, Jupiter Mahadasha, Ashtakavarga query. Each records the query, metadata filters, retrieved rule IDs, chapters and pages.

Acceptance criteria

  • AC1. Every chapter in both volumes appears in chapter_map.json with separate printed and PDF page fields.
  • AC2. validate_jsonl.py reports zero duplicate rule IDs and zero missing source_text; all needs_review items are listed.
  • AC3. All 12 house files and the other category folders are populated from the source, with no invented rules.
  • AC4. Retrieval for each test case returns relevant rules with full source citations.
  • AC5. A sample end-to-end reading shows the three separated layers (chart facts, classical rules, synthesis), each rule cited.
  • AC6. All ephemeris tests pass.

13. Risks and Mitigations

Risk Mitigation
PDF text/OCR errors in the translation needs_review flag, review report, manual verification of flagged pages.
Printed vs PDF page mismatch Two separate fields, never assumed equal.
Chapter number ≠ house number Assign house by actual BPHS chapter structure.
LLM hallucinating rules Strict prompt, retrieved-only context, traceability checks.
Wrong timezone or historical DST for birth place Use a proper timezone database; preserve all conversion inputs and outputs.
Embedding dimension mismatch Derive vector dimension from the selected model.
Copyright of the BPHS translation Private use, provenance preserved, no public redistribution.
Scope creep Section 3 non-goals; build the simplest working version first.

  3. LLM and embedding providers are not chosen (both are configurable).
